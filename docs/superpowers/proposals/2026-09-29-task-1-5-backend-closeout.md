# Task 1.5 backend closeout clarification — proposal

**Status: approved 2026-09-29, but the first replay trial failed its strict restore assertion; closeout is blocked pending a further decision.** This document defines a bounded amendment to the Task 1.5 *backend-correctness* gate. It does not amend the original §3.2 probe, the existing `test_single_rack_step_is_local_and_matches_probe`, its 500–1000 s bound, or its neighboring-rack assertion. That test remains a recorded failure.

## Why a separate gate is needed

The historical test combines FMU integration with a physical-response expectation taken from a different cold-start protocol. Its last recorded run failed at **1240 s by the test's index calculation**; the unchanged-load diagnostic gave **1260 s by that calculation**, and a matched no-step control showed substantial drift after the 7200 s warm-up. The exact cold-start §3.2 protocol reproduced its approximately 750 s crossing. These results characterize protocol-dependent FMU behavior; they do not establish a backend stepping error or invalidate the historical bound. The exploratory characterization chain is closed for this closeout decision.

## Proposed independent replay gate

Add one FMU-tier test and a **test-only** direct FMPy reference helper. The direct helper must not import `thermorl2.thermal.fmu_backend`, `thermorl2.raps_adapter.coupling`, or RAPS. It resolves the FMU's named value references independently, uses explicit Lassen constants (`0.945`, one rack per CDU, 290 K default ambient), and calls the FMI 2.0 Co-Simulation lifecycle and `setReal`/`doStep` directly. It runs in a separate OS process because the FMU allows one instance per process.

1. In both processes, instantiate the same SHA-256-pinned Lassen FMU with `setupExperiment(tolerance=1e-5, startTime=0)`. Apply **exactly 7200 s** of 10.86 kW on all 44 racks at 20 s steps, then save the FMU state. For the backend helper, use `warm_up(..., max_s=7200, settle_k_per_min=0.0)` solely to force this fixed-duration capped preconditioning and assert **`warmup_used_s == 7200.0` exactly**. This forcing relies on the current strict `<` settlement comparison in `warm_up`; a negative threshold would remain robust if that comparison ever became `<=`. Record the state as **capped/preconditioned, not settled**.
2. Replay this fixed four-phase sequence, 12 ticks per phase at 20 s/tick (960 s total). For zero-based rack index `i` and phase `j=0,1,2,3`, set `rack_kw[i] = [8.0, 10.86, 15.0, 25.0][(i+j) % 4]`. In phase 2 only, override rack 1 to 40.0 kW and rack 44 to 5.0 kW. Use `t_air_k=t_ext_k=290.0` for phases 0–1; use `t_air_k=289.0`, `t_ext_k=291.0` for phases 2–3. These are fixed engineering test vectors, not changes to the Task 1.5 workload or scientific operating assumptions. They exercise every rack input, the index mapping, phase changes, and the air/external input distinction.
3. In each process, record the snapshot observation at elapsed time zero and every post-snapshot tick: all 44 cabinet coolant temperatures, all 44 CDU primary supply/return temperatures, datacenter primary flow, the exact 44 rack-power and FMU heat-input values, both ambient inputs, elapsed time, and FMI communication time. Restore the saved state and replay the **same** sequence a second time in that process.
4. Compare direct versus backend arrays at corresponding communication points with `rtol=0` and predeclared `atol=1e-6` in the variable's native output unit (°C or GPM). Assert **equal elapsed-time arrays in the two processes**. Instrument the backend helper's actual `doStep` calls and assert at every tick that its communication point equals **`snapshot_time_s + elapsed_start_s`**; the observation after that step is at `snapshot_time_s + elapsed_end_s`. Compare those points with the direct helper's points, and assert finite outputs, exact prescribed input vectors, and 44-rack ordering. Within each process, first and restored replays must agree at `atol=1e-9`, `rtol=0`. Assert the backend's `runtime_s() > 0` and that calling `close()` twice succeeds. Save hashes and a compact comparison manifest. Any discrepancy beyond these tolerances stops Task 1.5 for debugging; tolerances are not widened after observing results.

This gate tests backend initialization, input application, observation conversion, snapshot time offset, and replay against the *same FMU accessed independently*. It does not assert a thermal time constant, spatial coupling strength, or equilibrium state.

## Warm-up language and downstream assumptions

`warm_up()` can end because its five-minute derivative criterion is met or because `max_s` is reached. **Using the full cap does not certify settling.** The existing test named `test_warm_up_settles_and_observe_shapes` checks a duration range and output shapes/limits, not the derivative criterion. In the observed 7200 s run, the following no-step hour cooled rack coolant by about **0.908 °C**; call that snapshot *capped* or *warmed*, never *steady idle*. Task 1.7's five-level uniform-load characterization must report the cap, measured no-load drift, and any `t_idle` reference as a capped snapshot value unless a measured settling criterion is actually satisfied. Keep its five levels and 45 °C assumption unchanged.

Later tests and rationales that inherit the unsupported fixed response-time premise are **not** silently cleared by this backend gate:

- The planned Phase 2 `tests/fmu/test_causal_coupling.py` asserts `450 <= t63 <= 1050` and `<0.5 °C` raw neighbor change from a staggered workload. It needs a separate physical/causal acceptance decision before execution; its power-distribution assertions are distinct.
- Design spec §11 asks the FMU tier to reproduce §3.2 within 5% and the Phase 2 rack response within 20% of the approximately 750 s cold-start probe. These are not equivalent to the plan's Task 1.5 500–1000 s or Phase 2 450–1050 s bounds. Preserve the historical statements and flag the mismatch for later review.
- Design spec §5.5 justifies `defer_reeval_s=60` as one-twelfth of a fixed rack time constant. That *rationale* is unsupported by the characterized state-dependent response. The 60 s fairness setting may remain provisional; it must not be presented as a validated thermal constant.

Task 1.6's engine/timing and cost checks and Task 1.7's five-level load sweep do **not** require a 750 s response bound. They can proceed under the separate backend gate, while Task 1.7 retains its own stop-and-report decision.

## First gate trial: blocked, not closed

The implemented test ran direct FMPy and the backend in separate processes against the same fixed sequence. **Both used exactly 7200 s of capped preconditioning, and their outputs matched exactly for every tick of both replay passes.** All prescribed time axes, actual backend `doStep` points, input vectors, and finite-output checks passed. However, replay 1 versus replay 2 within *each* process differed transiently by up to **0.000143434 °C** in rack coolant at elapsed 740 s. The approved within-process `atol=1e-9` assertion therefore fails for both direct FMPy and the backend. The full manifests and metrics are retained in [`task_1_5_backend_replay_trial`](../../../thermoRL/thermorl-v2/artifacts/diagnostics/task_1_5_backend_replay_trial/README.md). The same direct output was byte-identical across fresh processes. Direct-only checks with the rollback-safe FMI flag and a freshly deserialized snapshot did not remove the transient. This observation does not establish that the FMU is wrong; it establishes that strict replay identity was not achieved with either access path under this sequence.

The three existing lifecycle tests passed, the historical physical-response test still failed at **1240 s** when its warm-up test ran first, and unit/integration returned **19 passed**. No acceptance tolerance has been widened, the historical test remains unchanged, **Task 1.5 is not closed**, and no commit or Task 1.6 work has occurred. The approved rule above remains unfulfilled. Before changing it, choose explicitly whether to (A) retain the strict intra-process identity requirement and continue investigating FMU state restoration, or (B) approve a differently framed backend-correctness gate requiring direct/backend agreement on both replay passes and matching direct-reference restore deviations, while reporting the FMU-access-path replay transient as a limitation. Option B would be a new acceptance clarification, not a silent tolerance adjustment.
